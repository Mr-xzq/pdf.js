## 核心原则

### 文件编码
为避免输出乱码，文件的编码统一用 UTF-8

### 以终为始，追求核心功能与迭代
我们的开发流程将遵循**“先设计，后实现”**的原则，以确保开发方向的清晰性和长期可持续性。

* **完整蓝图先行**：在编码前，我将提供一个**完整且最优的实现方案**，该方案旨在追求功能的健壮性和可扩展性。这个蓝图将作为我们开发工作的北极星，确保每一步都朝着最终目标前进。
* **分步迭代，聚焦 MVP**：基于完整蓝图，我们将优先实现**最小可行产品（MVP）**。MVP 版本将只包含最核心的功能，以实现快速上线和验证。在编码过程中，我会确保 MVP 的实现方式与最终方案兼容，从而有效避免未来不必要的重构。
* **明确的后续步骤**：完成 MVP 后，我将提供一份清晰的**后续开发清单**。这份清单将详细列出为实现完整蓝图，下一步需要完成的功能和优化点。这有助于我们系统地推进项目，确保每一步都清晰、有序。

### 追求卓越的代码质量
我们将严格遵守以下编码规范和实践，以确保代码的**可维护性、可读性和一致性**。

* **简洁明了的命名**：文件、变量和函数将使用**简洁、直观、易懂**的命名，**避免不必要的缩写**。
* **统一的编码规范**：所有代码将遵循 **ES6+** 规范。
* **单一职责与适度拆分**：无论是组件还是函数，都应遵循**单一职责原则**。我们将复杂功能拆解为独立的、可复用的模块，以降低心智负担，同时**避免过度拆分**，以免因逻辑分散而增加认知成本。
* **简洁高效的文档**：除非另有明确要求，我将把所有的代码说明和注释都直接写在代码文件中，**不会创建额外的临时 `.md` 文件**。

### 健壮性、易用性与基于事实的决策
我将致力于在功能实现中平衡健壮性与易用性，并基于实际情况做出专业决策。

* **平衡健壮性与易用性**：我们设计的组件和函数将同时具备**良好的健壮性和易用性**。我将通过减少需要使用者决定的 `props` 来简化使用，并在功能的可扩展性和易用性之间取得最佳平衡。
* **基于事实的决策**：我的所有建议和方案都将基于**当前项目的实际情况**（如已有代码、依赖项）或**业界公认的最佳实践**。如果你的想法存在潜在问题或有更好的替代方案，我会提出并与你共同探讨，确保我们共同做出最佳决策。


## 技术栈偏好

* **样式**：优先使用 **Less**。如果需要在 Vue 组件中将样式抽离到单独的文件，我会创建 `.less` 文件。
* **JavaScript**：使用 ES6 或更稳定的最新语法。
* **Vue**：
    * 在组件上下文中，尽量使用 Vuex 提供的 `map` 映射函数（如 `mapState`、`mapGetters`、`mapMutations`、`mapActions`）来访问 store，以提高代码的可读性和可维护性。
    * 在渲染结构高度动态、模板表达力受限时，可以考虑使用 **render 函数 + JSX 语法**。
    * 在非 Vue 组件上下文中（即无法直接访问 `this.$store` 的地方），我会使用**静态导入**方式 (`import store from '@/path/to/store'`) 来访问全局 store。


## 文档和注释

* **行内注释和文档字符串**：为了提高代码可读性，我会在源文件中添加**行内注释和文档字符串**。但是，我会确保注释是有效的、有意义的，并且不会增加心智负担。
* **文档结构**：除非有你的明确批准，否则我**不会**创建新的 `.md` 文件。如果需要编写文档，我会先列出**确切的文件路径**并等待你的同意。对于现有文档，我会**原地更新**，并使用稳定的标题，以避免文档的蔓延和冗余。
* **计划与待办事项**：所有计划、笔记、待办事项等临时信息都将**仅在聊天回复中展示**，而不会被写入代码库中。


## MCP 调用规则

### 全局策略

我们的目标是为 Augment Code 提供安全、高效且可追溯的外部服务调用能力。所有工具调用都必须遵守以下原则：

- **单一焦点：** 每轮对话中，我们只调用一种最能解决当前问题的工具，避免无意义的并发。
- **结果精炼：** 默认只返回关键要点和必要的来源引用。
- **最小化原则：** 仅抓取解决问题所需的最小信息量，例如收敛查询范围、结果数或时间窗口，以减少噪声和资源浪费。
- **可追溯性：** 所有调用必须在答复末尾附上简报，确保每一步操作都有据可查。
- **稳健优先：** 面对失败，优先采用本地保守方案或执行降级策略。

### Playwright (浏览器自动化)

**用途：** 模拟真实用户的行为，与动态网页进行交互，执行端到端测试。

**调用时机：** 当需要模拟用户行为、获取浏览器上实际界面信息、或与动态加载的网页交互时。

#### 调用流程

1.  **意图判定：** 当用户需求涉及“查看网页界面”、“模拟点击/填写”、“检查控制台报错”、“布局调试”等，则优先考虑 Playwright。
2.  **前置检查：** 确保任务不涉及敏感信息，且无法通过离线或更简单的方式解决。
3.  **参数设定：** 确定最小必要的查询范围，例如指定关键词、目标元素或抓取页数。
4.  **执行与降级：**
    - 执行调用，并遵守设定的速率限制。
    - 如果调用失败（如网络错误、超时），按预设的重试机制执行。若多次失败，则提供一个本地保守的答案，并明确告知用户结果可能不准确。
5.  **生成简报：** 在最终答复后追加“工具调用简报”。

#### 工具调用简报 (必选)

为了保证可追溯性，每次调用后必须在答复末尾追加简报，其格式如下：

**【工具调用简报】**
- **工具：** Playwright
- **触发原因：** [简要说明调用原因，如“需要检查网页元素布局”]
- **输入：** [摘要输入关键词或 URL]
- **关键参数：** [如 `results: 10`, `timeout: 3s`]
- **结果概览：** [简要总结结果，如“成功获取标题”]
- **时间戳：** [调用完成时间]
- **来源：** [如 `http://example.com`]
- **重试：** [如果失败，记录重试次数及退避信息]
